# Verification and Conformance Gates

This specification turns principles 000, 001, 002, 007, and 008 into release
gates. A gate is complete only when the real `gsh` executable passes through
its public interfaces on every supported platform. Delegating behavior to
another shell is recorded separately and is never evidence of native
POSIX.1-2024 conformance.

The normative language source is the Open Group's official
[POSIX.1-2024 Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html).
Runtime requirements additionally follow
[`specs/0002.real_time.md`](0002.real_time.md).

## Evidence states

Every requirement has exactly one evidence state:

- `missing`: no implementation or executable test exists;
- `delegated`: observable behavior is supplied by another shell or runtime;
- `partial`: first-party native code exists but the normative cases are not
  complete;
- `verified-macos`: the complete gate passed on the supported macOS matrix;
- `verified-linux`: the complete gate passed on the supported Linux matrix;
- `verified`: both required platform states are present for the same revision.

Passing a differential test is insufficient when both implementations are
allowed to choose different behavior, or when `gsh` delegates to the reference
shell. Each test case therefore records its relevant POSIX section, whether the
result is prescribed, implementation-defined, unspecified, or undefined, and
whether the exercised path is native.

The implementation chooses the Issue 8-permitted behavior of never
substituting a token that is recognized as a reserved word and of inserting a
space after every replacement value. Both choices are testable and avoid
depending on unspecified token concatenation.

The parser treats each command substitution as one complete `compound_list`.
Issue 8 permits this choice, so an `alias` or `unalias` executed inside that
list need not affect later token recognition in the same substitution. The
same-revision executable evidence and comparative measurements are recorded
locally, when present, in the ignored files
`dev/status/2026-08-27-alias-matrix.md` and
`dev/performance/2026-08-27-macos-arm64-alias.md`.

Function mutations now cross the evaluator boundary as a versioned,
generation-checked, variable-size snapshot. The parent validates every source,
AST, word, redirect, name, hash, count, and bound before swapping stores;
malformed and interrupted writes retain the previous namespace. Structural
unit tests, ASan/UBSan, deterministic fault injection, parser/store fuzzing,
PTY fuzzing, and resource-pressure recovery cover this implementation. This is
`partial`, not platform verification: the full soak, performance comparison,
error/search semantics, and same-revision macOS/Linux matrix remain open.

The latest executable evidence for the mandatory arithmetic-expression
operators, assignment side effects, nested expansion, diagnostic categories,
interactive and non-interactive error behavior, isolation, bounded failure and
comparative cost is recorded locally, when present, in the ignored file
`dev/status/2026-08-27-arithmetic-diagnostics-matrix.md`.
It does not promote the whole word-expansion row because other expansion
requirements remain unverified.

The table must be updated only from executable evidence. Source inspection can
show that a feature is native, but cannot by itself promote a row to a verified
state.

## Real-time and reliability gates

### Build and source policy

- all first-party production and supporting executable sources are C;
- clean C17 builds use the POSIX.1-2024 feature-test baseline;
- warnings are errors on Clang and GCC;
- AddressSanitizer and UndefinedBehaviorSanitizer pass where supported;
- production binaries contain no test fault-injection behavior;
- build artifacts stay outside version control.

### Functional PTY gate

The compiled C harness launches the real executable in a controlling PTY and
verifies terminal modes, process groups, signals, job transitions, direct and
compound execution, state persistence, worker generation behavior, malformed
worker messages, worker crashes, deadlines, and terminal restoration.

### Fuzz and property gate

Fuzzing enters only through public parser or executable interfaces. Corpora
cover valid and invalid token streams, nested substitutions, here-documents,
redirections, expansions, patterns, environment data, worker frames, and PTY
byte streams. Every crash, sanitizer failure, unbounded run, descriptor leak,
or semantic invariant violation is a failure. Regression inputs are retained
as bounded corpus files.

### Fault-injection gate

Test-only builds provide deterministic one-shot failures at syscall and
component boundaries. Required points include pipe and socket creation, fork,
exec, descriptor duplication, open, allocation, poll, clock, terminal handoff,
worker crash, malformed frame, channel close, delay, and stale response. Tests
must prove exact-once command acceptance, bounded recovery, worker containment,
process cleanup, diagnostic classification, and terminal restoration.

### Resource-exhaustion gate

Black-box scenarios lower `RLIMIT_NOFILE`, `RLIMIT_NPROC`, and address-space or
data limits where supported; saturate fixed queues; exceed line, argument,
environment, expansion, here-document, job, and captured-output budgets; and
exercise disk-full and write-failure paths. Optional work is rejected first and
the shell either remains usable or exits with the terminal restored.

### Soak gate

The C harness runs repeated edit, dispatch, pipeline, signal, background-job,
directory-change, worker-refresh, and cancellation cycles for a configurable
duration. It samples resident memory, open descriptors, child count, deadline
misses, and terminal state. Counts must remain within declared bounds and all
children and temporary resources must be gone at completion.

### Platform matrix

Every candidate revision runs on current supported macOS arm64 and Linux
x86_64 with both Clang and GCC where available. Artifacts contain compiler,
kernel, CPU, terminal size, `TERM`, comparison-shell versions, test profile,
raw latency samples, sanitizer availability, and each gate result. A platform
that cannot run a sanitizer records `unsupported`; it does not silently record
`passed`.

## Release rule

`gsh` may be described as POSIX.1-2024 conforming and mission-grade only when
every POSIX row and every reliability gate above is `verified` for the same
revision. Until then, documentation and diagnostics state the remaining gaps
without converting delegated behavior into native credit.
