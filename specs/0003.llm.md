# LLM Integration

Genshell's LLM layer turns user intent and runtime observations into structured plans and results. It is replaceable, provider-independent, and isolated from the correctness-critical shell core.

> **LLMs are composable Unix primitives, not terminal chatbots.**

The computer, not the model, is the center of the product. Models reason about requests and observations; Genshell owns context, capabilities, execution, verification, and the interface to the operating system.

## Goals

- Make `?` a native primitive for expressing intent in the `gsh` operating language.
- Preserve shell-native context without forcing the user to restate what just happened.
- Compose LLM processing with standard input, standard output, pipelines, and structured data.
- Support interchangeable cloud, subscription-backed, and local providers.
- Allow provider selection per request, per session, or persistently in [`~/.gshrc`](0006.gshrc.md).
- Generate typed plans and native Genshell operations rather than treating Bash as the computer's only API.
- Keep every generated command and native operation observable.
- Keep the interactive shell fully functional when AI is disabled, unavailable, slow, or faulty.

## Non-goals

- Adding a chat panel beside a traditional shell.
- Reducing the feature to natural-language-to-Bash translation.
- Letting a provider execute actions directly or own OS capabilities.
- Coupling the shell core to one model, vendor, authentication method, or network service.
- Sending the complete shell state, environment, history, or filesystem to every request.

## Invocation model

Command mode and intent mode coexist in the same language:

```text
gsh$ git status
gsh$ ? summarize the current repository state
```

`?` can use the current operational context:

```text
gsh$ make
...error...
gsh$ ? why did that fail?
```

It can also participate in Unix pipelines:

```text
gsh$ git diff | ? show only potentially dangerous changes
gsh$ ps aux | ? identify anomalous processes
gsh$ cat access.log | ? group errors by probable root cause
```

An intent invocation may produce:

- a direct answer;
- a structured result;
- a proposed or executable Genshell plan;
- one command or an ordered command sequence;
- a rich result for the Genshell terminal.

The provider does not decide whether an operation is authorized. It returns content or a proposal; the Genshell runtime validates and executes it under the active capability and effect policy.

## Operational context

Genshell owns a persistent, structured context that may include:

- current working directory;
- selected environment values;
- command and action history;
- the previous exit status;
- bounded `stdout` and `stderr` from relevant commands;
- active processes, jobs, and pipelines;
- terminal and PTY state;
- referenced filesystem resources;
- observations from [OS Automation](0005.os_automation.md);
- reversibility metadata from [Rewind](0004.rewind.md).

Context is assembled per request rather than copied wholesale. The runtime selects the smallest relevant set, retrieves additional data lazily, and summarizes older observations when necessary to remain within the provider's context limit.

Every context item carries provenance, such as `user`, `runtime`, `command_output`, `file`, `external_content`, or `provider_output`. Retrieved files, web content, logs, and application UI are treated as untrusted data rather than as authority to change the user's request or Genshell policy.

Secrets, secure fields, credentials, protected clipboard content, and sensitive environment variables are excluded or redacted by default. Rewind snapshot contents are never included automatically.

## Provider abstraction

Every provider implements a versioned contract for:

- capability discovery;
- model discovery and selection;
- authentication state;
- streaming text and structured results;
- cancellation and deadlines;
- context and output limits;
- supported modalities;
- usage and quota metadata when available;
- stable provider errors.

Provider capabilities may differ. The runtime records whether a model supports structured output, images, tool schemas, local execution, streaming, or other optional features and routes only compatible requests to it.

A provider response is never executable merely because it was emitted by a trusted model. Structured responses must pass schema validation, and free-form text remains data until explicitly parsed and validated by the runtime.

## Configuration model

Provider configuration is available at three operational levels.

### Per request

The user can select or constrain the provider conversationally for one invocation:

```text
gsh$ ? use the local model for this task: summarize these logs
gsh$ ? use Codex to review this diff
```

The override belongs to that request and is recorded with the resulting action.

### Per session

Provider commands change the current shell session without modifying persistent configuration:

```text
gsh$ provider list
gsh$ provider status
gsh$ provider use codex
gsh$ provider use local:ds4
gsh$ provider use auto
```

### Persistent configuration

Defaults, provider options, and routing policy live in [`~/.gshrc`](0006.gshrc.md):

```text
llm.default_provider = auto

llm.providers.codex.auth = chatgpt
llm.providers.openai.model = gpt-default
llm.providers.local.engine = ds4
llm.providers.local.model = local-default

llm.routing.allow_cloud = true
llm.routing.sensitive_data = local_only
```

The names above define configuration semantics, not a fixed model catalog. Installed providers expose their current models through capability discovery.

Configuration precedence is:

```text
request override → session override → active profile → ~/.gshrc → automatic selection
```

The complete configuration-source order, including user fragments and system defaults, is defined in [`~/.gshrc`](0006.gshrc.md).

Authentication secrets are never stored in plaintext in `~/.gshrc`. The file may select an authentication method or reference a credential name; tokens and account sessions belong in the OS credential store or provider-owned secure storage.

## Providers

The initial provider architecture should accommodate:

- Codex through a ChatGPT subscription where supported;
- OpenAI API access;
- local models through llama.cpp;
- local models through DS4;
- local or remote Ollama instances;
- future provider plugins.

Provider-specific behavior remains behind the shared contract. Plans, effects, execution, history, and OS access do not change when the provider changes.

## Codex subscription

The Codex provider may integrate with Codex App Server and the user's ChatGPT authentication where supported. This allows an eligible user to use subscription-backed Codex access without configuring a separate API key.

Conceptually, setup can offer:

```text
gsh$ setup

Choose AI:
1. ChatGPT / Codex subscription
2. OpenAI API
3. Local model
4. None
```

Codex is a reasoning provider and client of Genshell's runtime. The shell, action model, OS capabilities, provider routing, and local state remain owned by Genshell.

Authentication expiry, quota exhaustion, login cancellation, and unavailable subscription access are normal provider errors. None of them may prevent command mode from working.

## Automatic routing

When `auto` is selected, a policy engine chooses a compatible provider using explicit signals:

- user and session constraints;
- local-only or cloud-allowed policy;
- data sensitivity;
- provider availability and authentication state;
- required modality and structured-output support;
- context size;
- expected latency;
- cost or quota metadata when available;
- local hardware and model availability.

The routing decision, provider, model, policy inputs, and fallback reason are written to the action journal.

Automatic routing never overrides `local_only`, sends redacted data in unredacted form, or silently enables a cloud provider forbidden by policy. Provider fallback is allowed only within the same policy boundary.

If a provider fails before execution, the runtime may retry with a compatible provider. If an action has already started, failover resumes only from a recorded observation or safe checkpoint and never replays completed side effects.

## Local AI

Local AI is a first-class, managed path rather than a manual installation recipe.

```text
gsh$ setup local

Detected: macOS arm64
Memory: 128 GiB unified
Acceleration: Metal
Recommended engine: ds4
Recommended model: local-default
Install? [Y/n]
```

The local provider manager can:

- detect OS, architecture, memory, GPU, Metal, CUDA, ROCm, and free disk space;
- recommend a compatible runtime and model;
- download a versioned prebuilt runtime;
- verify its hash and signature;
- install it under a Genshell-owned directory;
- download models with resume support;
- register installed models as providers;
- start, monitor, and stop local provider processes.

Conceptual layout:

```text
~/.genshell/
  runtimes/
    llama.cpp/
    ds4/
  models/
```

The end-user path must not require Homebrew, Python environments, npm, or manual compilation. Local runtimes run outside the shell core, and their crashes or resource exhaustion cannot corrupt normal shell state.

## Structured planning and execution

The preferred execution loop is:

```text
intent
  ↓
selected context
  ↓
provider response
  ↓
typed plan validation
  ↓
capability and effect policy
  ↓
OS Automation runtime
  ↓
execute → observe → verify → adapt
  ↓
Rewind journal + structured result
```

Providers never call the operating system directly; execution crosses the [OS Automation](0005.os_automation.md) boundary and every result is recorded by [Rewind](0004.rewind.md).

A plan step includes:

- operation and typed arguments;
- required inputs and dependencies;
- expected effect classes;
- capabilities requested;
- preconditions and postconditions;
- deadline and cancellation behavior;
- safe retry semantics.

The runtime derives and validates effects and capabilities independently. Model-provided classifications are hints, not authority.

Malformed or unknown operations are rejected. A bounded repair attempt may ask the provider for a corrected structure, but unparsed free-form output is never executed as an implicit plan.

When the user requests commands, or when the validated plan intentionally uses shell commands, every exact executable command is rendered in full and in execution order. Native OS operations receive an equally explicit human-readable representation.

## Unix composition

`?` consumes standard input when placed in a pipeline and can emit traditional text, structured records, or both.

The contract preserves:

- `stdin`, `stdout`, and `stderr` separation;
- exit status;
- backpressure and cancellation;
- bounded buffering or spooling for large inputs;
- downstream compatibility with traditional Unix tools.

The Genshell terminal may receive a second structured channel for tables, charts, progress, images, notifications, and interactive actions. When the client does not support rich output, the result degrades to ordinary text without changing its meaning.

AI work is asynchronous relative to the interactive core. A slow provider may delay its own result, but it must never block typing, prompt rendering, job control, or unrelated shell activity.

## Safety and privacy

- Providers receive only context selected for the current request.
- Cloud transmission follows explicit routing and data-sensitivity policy.
- External content is data, not permission and not a source of higher-priority instructions.
- The runtime validates every structured plan before execution.
- Capabilities, permissions, approvals, and effect classification belong to Genshell, not to the provider.
- Secure values are redacted from prompts, logs, provider traces, and model-visible history by default.
- Provider responses cannot bypass OS permission surfaces or [OS Automation](0005.os_automation.md) capability checks.
- [Rewind](0004.rewind.md) records provider, model, routing decision, context references, plan, result, and reversibility state without automatically storing sensitive prompt payloads or snapshot contents.

## Observability

Every invocation has a stable request identifier and records:

- selected provider and model;
- configuration level that selected them;
- routing and fallback reason;
- referenced context items and their provenance;
- streaming, cancellation, and completion state;
- validated plan and displayed commands, when any;
- usage and quota metadata when available;
- final result, error, and associated action identifier.

Users and agents can inspect this metadata through provider status and action-history interfaces. Normal successful operation remains concise; detailed traces are available on demand.

## Reliability and failure isolation

- The shell core never depends on provider initialization or network availability.
- Provider calls run outside the latency-critical interactive path.
- Every request has a deadline and cancellation path.
- Stale completions are discarded when their request or context has been superseded.
- Provider queues, context assembly, and streaming buffers are bounded.
- Provider crashes, malformed events, and partial streams return stable errors.
- Failover cannot duplicate commands or native side effects.
- AI-disabled mode remains a fully functional shell configuration.

## Current native implementation slice

The first operational slice uses a separate native C worker for an OpenAI
Responses API-compatible endpoint. DS4, llama.cpp, and custom endpoints share
the same provider contract and persistent configuration in `~/.gshrc`.
Responses stream into the owning classic job or managed REPL cell; the worker
replays a bounded local prompt/answer history with `store: false` and supports
bounded `history_search` and guarded `run_cli` function calls. Every `run_cli`
call crosses a bounded private channel into a new ordinary REPL command cell,
identified by a visual `[AI]` tag outside the script and history text. The
worker cannot execute generated scripts itself. The owning reactor applies
the same execution and state-commit rules used for typed shell commands and
returns the cell identity, exit status, bounded output, and session directory
only after command completion and output closure. Assistant continuation moves
to a subsequent cell so transcript order reflects actual tool execution.
Unstarted commands with stale session context are rejected explicitly; user
commands accepted after a generated command retain normal execution ordering.
Cancellation closes the channel and cancels outstanding work without undoing
completed effects. AI work initiated from classic mode enters the managed
cell view for the current session; `/async` remains the return control.
Only recognized removal operations require execution confirmation. All other
scripts run automatically, including session changes, writes and unfamiliar
commands. The bounded policy parses executable words and literal shell
wrappers/substitutions; printed removal names and quoted heredocs do not trigger
approval. The model is instructed to use explicit removal CLIs, since this
syntax classifier does not infer arbitrary program effects. Rejection leaves
the proposed script unexecuted and returns a cancellation receipt to the model.
The worker reports startup, generation and confirmation phases over its private
channel. The compositor displays a green spinner after `gsh ai>` during
generation, including streaming, without a label. Startup adds muted
`Starting...`; confirmation uses muted `Awaiting confirmation` and stops the
spinner. No animation or status decoration enters captured output or history.
The pipeline
form executes its left side once and disables execution tools for that request.

The setup implementation detects RAM, CPU count, free storage, Metal, CUDA,
ROCm, and whether the corresponding GPU build toolchain is actually usable.
It selects DS4's build target and Q2/Q4 resident-versus-SSD policy from that
profile. For llama.cpp it selects the largest suitable entry from a fixed,
reviewable ten-model GGUF catalog, marks every alternative as fitting or
oversized, permits a custom repository reference, and compiles the matching
Metal, CUDA, HIP, or CPU backend. A model or backend recommendation is never an
installation authorization: large downloads still require confirmation.
Managed DS4 and llama.cpp processes share a provider-scoped activity lease.
Their detached supervisor sends `SIGTERM` to the owned process group only
after `runtime.idle_timeout` has elapsed with no active request, then escalates
to `SIGKILL` after a bounded grace period. Concurrent requests and tool
confirmations keep the lease active; attached external servers are never
terminated.

This slice deliberately implements less than the complete architecture above:
it has one configured default provider, one process-backed cancellation unit,
and a coarse serial AI lane. Per-request/session routing, capability discovery,
typed native plans, generation-preserving steering, rich output, and policy
failover remain future work. The exact user-facing behavior and current
configuration keys are documented in the repository `README.md`.

The current journal writer is an isolated process. The reactor enqueues at
most 256 KiB of framed records and transfers at most 8 KiB per service turn;
disk access, advisory locking, checksumming and synchronization occur outside
the editor owner. Queue saturation or writer failure reports lost records
without changing command status or ordinary shell history. Shutdown drains
for at most 250 ms before terminating a stalled writer. Each frame captures
its destination HOME when accepted. A record retains at most 64 KiB; rotation
at 1024 prompts, 8192 records, or 4 MiB keeps one previous file and recovers
from a torn tail before appending new data. Readers preserve their output
capacity even when a label and terminator leave no room for payload text.

## Verification

The test suite uses deterministic mock providers plus compatibility tests for installed providers. It verifies:

- `?` in interactive mode, after failed commands, and inside pipelines;
- context selection, provenance, truncation, summarization, and lazy retrieval;
- exclusion of credentials, sensitive environment variables, secure UI values, and Rewind snapshot contents;
- treatment of files, logs, web pages, and UI content as untrusted data;
- provider capability discovery and configuration precedence;
- per-request, per-session, persistent, and automatic provider selection;
- authentication failure, offline mode, quota exhaustion, and unavailable providers;
- local runtime detection, installation integrity, lifecycle, and crash isolation;
- structured-plan validation, malformed output, bounded repair, and unsupported operations;
- exact visibility and ordering of generated commands;
- effect and capability validation independent from model claims;
- streaming, backpressure, timeouts, cancellation, stale-result rejection, and bounded queues;
- provider failover without duplicate execution;
- text fallback and rich structured output;
- [OS Automation](0005.os_automation.md) execution and [Rewind](0004.rewind.md) journal integration;
- unchanged shell behavior and latency when AI is disabled.
