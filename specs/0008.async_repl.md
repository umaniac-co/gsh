# Asynchronous REPL

Genshell is an asynchronous command surface. Accepting one instruction does
not make the next editor wait for that instruction's output or completion.

> **The next thought does not wait for the previous result.**

This specification defines the interactive submission, rendering, scheduling,
and AI-steering semantics required to make that statement true. It extends the
soft real-time reactor in [Real-Time Shell Core](0002.real_time.md) and the
intent model in [LLM Integration](0003.llm.md).

The LLM runtime does not exist yet and is not implemented by this
specification. The AI sections define identities, state transitions, and
observable behavior so the asynchronous REPL can be built without later
changing its foundations.

## Goals

- Activate a fresh editor immediately after every complete interactive
  submission, independently of output and completion.
- Give every submission a stable identity and an output cell that reserves
  one logical row by default and grows when more output arrives.
- Preserve the active edit buffer while any number of bounded, concurrent
  output streams advance, stop, fail, or finish out of order.
- Execute independent submissions concurrently while keeping shell-state
  reads, mutations, status dependencies, and commits deterministic.
- Keep the physical terminal owned by `gsh` while managed asynchronous mode is
  active, and give terminal-dependent jobs faithful virtual terminals.
- Route keyboard input and job-control signals through deterministic input
  focus, including automatic focus for private terminal input.
- Make a standalone `?` steer the active AI request while it is still active.
- Make a standalone `??` create a distinct AI request in a bounded FIFO queue.
- Preserve exact execution, visible output ownership, cancellation, terminal
  integrity, and bounded behavior under overload.
- Retain a classic direct-terminal mode and unchanged non-interactive behavior
  for POSIX compatibility and programs that require it.

## Non-goals

- Implementing an LLM provider, context assembler, planner, or AI executor in
  the current MVP.
- Treating one printed newline character as an output cell.
- Allowing external processes to write uncontrolled escape sequences directly
  to the physical terminal in managed asynchronous mode.
- Guessing that every accepted command is safe to run concurrently.
- Making completion order define shell-state order.
- Silently dropping output, accepted submissions, steering events, or queued
  AI requests when a resource limit is reached.
- Guessing whether editors, pagers, debuggers, or nested REPLs need input from
  their displayed text; programs without a detectable private-input
  transition remain explicitly focusable.
- Changing POSIX script, `-c`, pipeline, redirection, or descriptor semantics
  merely to obtain a convenient display.

## Terminology

- **Submission**: one complete interactive instruction accepted by `gsh`.
- **Sequence**: the monotonic session order assigned to submissions.
- **Cell**: the logical presentation record containing the submitted text,
  output, status, and lifecycle of one submission.
- **Active editor**: the one mutable command line that owns ordinary keyboard
  input when no job has explicit input focus.
- **Command job**: the process group or reactor-owned operation executing a
  submission.
- **Session state**: current directory, variables, aliases, functions,
  options, positional parameters, and other state owned by the shell process.
- **Dependency**: an unresolved earlier result or session-state mutation that
  a later submission must observe before it can execute correctly.
- **Input focus**: the exclusive routing of keyboard bytes and terminal
  signals to one command job instead of the editor. Focus may be selected
  explicitly or acquired automatically from a trusted PTY-mode transition.
- **AI request**: one user intent with a stable request identity.
- **AI generation**: one provider attempt or revised response within the same
  AI request.
- **Steering**: a user correction that supersedes the unfinished generation of
  the active AI request without creating a separate request.
- **Queued AI request**: a distinct AI request waiting for the session AI lane
  in FIFO order.
- **Settled session**: a session in which every retained submission is in a
  terminal state and every associated output source is closed, with no pending
  PTY input or output. Success, failure, cancellation, and rejection are all
  terminal outcomes; a terminal outcome with an open PTY is not yet settled.

## User-visible contract

For a terminal large enough to display the standard layout, Enter on a
complete command atomically produces this state:

```text
[main] [●] $gsh> long-running-command

[main] [○] $gsh> _
```

The row is logical reserved space, not one byte or one unconditional newline
write. It has no visible separator or indentation. Output fills that row and
then expands the cell:

```text
[main] [●] $gsh> long-running-command
first line
second line
third line
fourth line
fifth line
sixth line
[main] [○] $gsh> next command being edited_
```

The transition has four indivisible user-visible effects:

1. the accepted text becomes immutable and receives a submission identity;
2. its cell and one-row reservation become visible;
3. the submission becomes `queued`, `running`, or synchronously `done`;
4. a new empty editor becomes visible and accepts input.

Failure to launch does not roll the editor back into the submitted line. The
cell becomes `failed`, carries the launch diagnostic and status, and the new
editor remains usable.

The default minimum is one logical row. A physically smaller viewport may
show fewer rows at once, but the cell retains its logical height in Genshell's
view model. Empty reserved rows remain part of the completed cell unless a
future explicit presentation policy collapses them; completion itself must not
make the active editor jump unexpectedly.

### Global completion indicator

The primary managed prompt contains one global indicator computed by a bounded
query over the sixteen retained cells:

- `[●]` means every preceding submission is settled and cannot produce more
  output;
- `[○]` means at least one submission is queued, starting, running,
  stopped, has pending input or output, or still owns an open PTY.

The empty set is settled, so a new managed viewport begins with `[●]`. A
failure, cancellation, or rejected launch contributes to `[●]` only after
its output source is closed. Completion order does not affect the query.

With a branch the exact prompt shape is `[main] [●] $gsh>` or
`[main] [○] $gsh>`; without a branch it is `[●] $gsh>` or `[○] $gsh>`.
The branch and indicator are rendered in a slightly muted gray within one ANSI
style span. Genshell explicitly resets terminal style before `$gsh>`, so the
shell marker, typed text, command output, and following rows retain the
terminal's default color. Continuation prompts, reverse search, and classic
mode have no completion indicator.

The compositor treats `●` and `○` as atomic one-column UTF-8 tokens. ANSI
sequences have zero visible width and are also atomic. Clipping and resize may
discard a complete token but never split a UTF-8 sequence or an ANSI style
sequence, and any active prompt style is reset at the clipping boundary.

## Cells and rendering

Cells are ordered by submission sequence, not by first output, last output, or
completion time. A late write remains associated with the cell whose job
produced it. Concurrent jobs cannot merge their output into an unattributed
terminal stream.

Every cell records at least:

- submission and action identity;
- immutable submitted text;
- submission kind and dependency state;
- lifecycle and exit status;
- process-group or AI-request identity when applicable;
- ordered output events with `stdout`, `stderr`, structured, and runtime
  provenance where those channels remain distinct;
- truncation, spooling, overload, cancellation, and failure markers;
- AI request and generation identity for intent cells.

The renderer owns a logical viewport and scrollback model. It may redraw the
visible tail, insert rows, coalesce frames, or use synchronized terminal
updates, but those choices cannot change cell order or output ownership. The
active edit buffer, cursor, selection, completion state, and continuation
prompt survive every redraw.

Terminal output is untrusted rendering input. In managed mode, control
sequences from a job are parsed within that job's virtual terminal or cell.
They cannot erase another cell, move the Genshell editor, replace the physical
terminal title without policy, inject a fake prompt, or escape their rendering
boundary. Unsupported sequences degrade visibly and deterministically.

Updating an old cell that has left the physical terminal's native scrollback
cannot be implemented reliably with cursor movement alone. Managed mode
therefore owns the logical scrollback required to redraw live cells. Copy,
selection, search, accessibility, resize, and restoration must be designed
against that owned representation rather than assumed from the hosting
terminal emulator.

## Terminal ownership architecture

The current direct foreground model is:

```text
physical terminal <──> foreground process group
                         gsh editor inactive
```

Managed asynchronous mode changes the boundary to:

```text
physical terminal <──> gsh reactor and compositor
                         ├── active editor
                         ├── job PTY A <──> process group A
                         ├── job PTY B <──> process group B
                         └── bounded cell and scrollback state
```

The physical terminal remains controlled by the Genshell process group. A job
whose unredirected descriptors require terminal semantics receives a PTY slave
with the correct window size, process group, signal dispositions, and terminal
modes. Explicit pipes and redirections retain their requested descriptor
topology. PTYs are used because ordinary output pipes would change `isatty()`,
buffering, colors, terminal modes, signals, and interactive behavior.

The reactor polls terminal input, signal notification, worker channels, and a
bounded set of job PTY masters. It consumes a bounded byte and event batch from
each ready source before returning to input and critical lifecycle work. One
high-volume job cannot monopolize a reactor turn or starve the editor.

No job, provider, worker, signal handler, or background callback writes
directly to the physical terminal in managed mode. All user-visible changes
pass through the reactor and compositor. This rule refines the direct terminal
handoff described in [Real-Time Shell Core](0002.real_time.md) when managed
asynchronous mode is active.

### Classic mode

Classic mode retains direct `tcsetpgrp()` foreground handoff, normal hosting
terminal scrollback, and the traditional exit-to-prompt lifecycle. It exists
for strict compatibility, diagnostics, unsupported terminal environments, and
programs whose behavior cannot yet be represented faithfully by managed mode.

Entering classic mode is explicit and visible. Genshell must not silently move
an already accepted managed job between a PTY and the physical terminal.

### Mode selection and `/async`

Managed mode is enabled by default. The typed configuration key
`shell.async_repl.enabled = true|false` selects the startup mode; an absent key
is equivalent to `true`, and a non-boolean value rejects the complete candidate
configuration transaction. If `GSH_REPL` is present, the exact value `classic`
forces classic mode and every explicit non-`classic` value forces managed mode.
The current session's `/async` override has the highest precedence and never
rewrites `~/.gshrc`.

Only the exact standalone interactive submission `/async` is control syntax.
Managed mode accepts it as a control submission and classic mode handles it
synchronously. It follows ordinary interactive history policy. Leading or
trailing whitespace, quoting, escaping, additional words, scripts, and `-c`
retain ordinary shell semantics.

The session records the effective mode, desired mode, and whether a transition
is pending. When the shell is quiescent, `/async` changes mode immediately.
Otherwise it reports `async repl: on pending` or
`async repl: off pending` and continues accepting commands under the effective
mode. A second exact `/async` cancels that request and reports
`async repl: transition cancelled; remains on|off`.

Quiescence requires no managed cell that is not settled, no pending PTY input
or output, no shell-state commit lane, no foreground job, and no live classic
background job. Switching off waits for the final compositor flush, leaves the
alternate screen, restores classic termios and signal routing, and discards
the completed managed viewport before reporting `async repl: off` with a
classic prompt. Switching on creates a fresh viewport, redetects terminal
capabilities and size, applies managed termios, enters the alternate screen,
and reports `async repl: on` with a settled managed prompt.

Non-interactive execution never creates cells and is unaffected by this
specification.

## Submission lifecycle

A submission moves through the following bounded lifecycle:

```text
accepted ──> queued ──> starting ──> running ──> done
                 │          │            ├────> stopped
                 │          └────────────┴────> failed
                 └────────────────────────────> cancelled
```

`accepted` is durable in session state before execution is attempted.
`queued` means that a declared resource bound or semantic dependency prevents
immediate dispatch; it does not mean the instruction was lost. `done`,
`failed`, and `cancelled` are terminal states with an explicit result.

Every accepted submission executes at most once. Retrying process creation,
provider transport, partial writes, or renderer commits cannot create another
submission identity or duplicate side effects.

The active submission registry, runnable set, PTY set, render buffers, retained
output, AI queue, and journal handoff are bounded. Reaching a limit produces an
explicit cell state or rejects acceptance before identity assignment. A cell
must never remain indefinitely ambiguous between accepted and rejected.

## Deterministic command scheduling

Immediate editing does not imply indiscriminate execution. Genshell schedules
submissions from explicit dependencies and a conservative classification of
their session-state behavior.

Each accepted command receives a sequence number. A command proven not to
depend on unresolved earlier session mutations or statuses may start while an
earlier command is still running. A command that might observe or mutate
unresolved session state remains visibly `queued` until its dependency is
settled. Unknown cases are dependencies; concurrency is never guessed for a
favorable latency result.

Compound syntax is not itself a dependency or a global execution fence. A
compound command uses the serialized state lane for its eventual commit, but
an independent external command may overtake it when the compound command has
no pending mutation that can alter that command's launch snapshot. Launch
state includes the working directory, exported environment, command lookup,
process settings, aliases, and functions. Unexported loop variables and status
changes do not block a command that does not reference them.

Classification and dispatch remain owned by the single reactor thread. The
classifier walks each accepted bounded AST at most once with fixed storage;
the scheduler scans the fixed cell registry and never takes a lock, waits for
a worker thread, allocates per decision, or retries an ambiguous dispatch.

Examples:

```text
$gsh> sleep 10
$gsh> pwd          # may run immediately from committed session state
```

```text
$gsh> for i in 1 2 3 4 5; do echo "row $i"; sleep 1; done
$gsh> git status   # starts immediately while the loop keeps producing output
```

```text
$gsh> sleep 10; cd /tmp
$gsh> pwd          # accepted immediately, queued behind the pending mutation
```

State-changing builtins and compound-command mutations retain main-shell
semantics. Their commits occur in submission order. A later state commit cannot
overtake an earlier mutation and make the final directory, variables, aliases,
functions, options, or positional parameters depend on timing. Independent
external jobs may complete first because they do not commit session state.

External jobs receive an immutable snapshot of committed session state at
dispatch. A later `cd` or environment mutation does not retroactively change a
running process. Filesystem, network, and other external side effects from
concurrently launched commands can naturally race; their concurrency is
visible through distinct running cells and recorded by the action journal.

`$?` refers to the status of the immediately preceding submission in sequence,
not whichever concurrent job happened to finish last. If a later command
needs that status before it is known, the dependency keeps it queued. Job
status remains directly addressable by stable job or submission identity.
Completion events never mutate status-dependent shell behavior according to
nondeterministic arrival order.

AND-OR lists, pipelines, loops, functions, and compound commands retain their
internal language ordering inside one submission. Asynchrony between cells
does not turn the operators within a command into implicit background syntax.

## Input focus and interactive jobs

The editor owns keyboard input after submission until one managed PTY makes a
detectable private-input request. Disabling terminal echo is such a request:
the reactor atomically gives that cell keyboard focus before processing a
simultaneously ready editor byte. Detection uses PTY state, never localized or
spoofable prompt text.

The transition requires no keyboard shortcut. The active editor line remains
in place with its complete edit buffer and default presentation while it does
not own input. The requesting cell receives subsequent bytes immediately.
When the focused process exits, fails, or stops, the editor resumes ownership
with its exact contents. If several cells request private input, the oldest
live request wins deterministically and the next request is considered when
focus becomes free.

Programs that read with echo enabled or do not expose a detectable PTY-mode
transition can still receive explicit focus through the job-control interface;
`fg` is the preferred semantic basis for that fallback.

A PTY that enters non-canonical mode requests a contained full-screen focus.
This applies by terminal behavior rather than command name, so curses programs,
editors, pagers, monitors, multiplexers, and interactive coding agents share
one path. The reactor pauses cell redraw, relays a bounded terminal-protocol
batch to the physical viewport, and continues to own input, signals, resize,
and lifecycle. UTF-8 scalars remain atomic across PTY reads; their continuation
bytes are never interpreted as standalone C1 controls. OSC, DCS, physical
alternate-screen changes, and window-control sequences are not relayed. Exit,
stop, failure, or `Ctrl-]` restores cursor,
mouse, paste, keyboard, and style modes before rebuilding the async viewport.
The retained cell records a compact full-screen-session marker rather than a
raw curses dump. `Ctrl-]` and `bg` suppress further autofocus for that job;
only an explicit `fg` restores its input focus.

While a job has focus:

- ordinary keyboard bytes go to its PTY;
- terminal-generated signals target its process group;
- terminal mode and window-size changes are reflected in its PTY;
- full-screen rendering is contained in its virtual terminal;
- the shell edit buffer remains preserved but does not consume the same keys.

Leaving focus restores the editor and its exact state. A focused program may
temporarily occupy the complete viewport, but focus never returns uncontrolled
physical-terminal ownership to the child.

With no focused job, `Ctrl-C` cancels the active edit or the explicitly
selected cancellable shell operation. With a focused job it signals that job.
`Ctrl-Z`, end-of-file, suspend, resize, terminal loss, and shell shutdown have
equally explicit routing and recovery rules.

Programs waiting for input must expose a visible waiting or focusable state
when Genshell can determine it. A private PTY transition triggers autofocus;
failure to detect a read is not permission to infer intent from output text,
and explicit focus remains the fallback correctness path.

## AI request lane

The interactive session has one ordered AI request lane. At most one request
in that lane is active by default. This makes the difference between steering
and queueing stable even when providers support their own internal
concurrency.

The standalone interactive control forms are:

| Input | AI lane before acceptance | Meaning |
| --- | --- | --- |
| `? request` | no active steerable request | Create and activate a new AI request. |
| `? correction` | an active steerable request exists | Steer that request with a new generation. |
| `?? request` | active or idle | Create a distinct request and append it to the FIFO queue; if the lane is idle, it may activate immediately. |

The decision is made atomically when the complete line is accepted by the
reactor. A completion observed before acceptance means there is no active
request to steer; a completion observed afterward belongs to the generation
that the accepted steering event supersedes.

Only an unquoted `?` or `??` recognized as the first command word of a
standalone interactive submission has this control meaning. Quoted or escaped
question marks are ordinary text.

The Unix primitive form defined by [LLM Integration](0003.llm.md), such as:

```text
$gsh> ps aux | ? identify anomalous processes
```

is a pipeline command with `stdin`, `stdout`, exit status, and backpressure. It
creates its own pipeline-bound invocation and never implicitly steers an
unrelated interactive request. Queueing and steering of composed pipeline
invocations require explicit future syntax; `??` in this specification is the
standalone REPL control form.

## Steering with `?`

Consider an active request:

```text
$gsh> ? what's the high-cpu usage process?
Inspecting the current process list...
$gsh> ? i meant memory
```

The second instruction does not create a new AI request. It creates a steering
event and a new generation under the original stable request identity:

```text
request 41, generation 1: what's the high-cpu usage process?
request 41, generation 2: i meant memory
```

Every steering event has its own submission and cell identity so the user's
correction remains visible in sequence. The earlier cell is marked
`superseded`; already displayed partial output remains auditable rather than
being silently rewritten. The revised generation streams into the steering
cell. Both cells link to the same AI request.

On accepted steering, Genshell:

1. records the correction and increments the request generation;
2. invalidates uncommitted proposals and undisplayed results from the previous
   generation;
3. requests cooperative cancellation of the previous provider generation;
4. starts or schedules the revised generation with the original request,
   correction history, and eligible updated observations;
5. discards any late provider events carrying a stale generation;
6. records the complete transition in the action journal.

A provider with native conversational steering may continue its session. A
provider without it is cancelled and restarted from a bounded immutable
request snapshot plus the ordered corrections. Provider capability changes
latency and transport, not user-visible steering semantics.

Rapid corrections are all recorded in acceptance order. Provider work for
superseded intermediate generations may be coalesced, but the final provider
context must preserve the meaning and order of every accepted correction.

Steering is not rollback. Commands or native effects that already executed are
never erased or repeated implicitly. A correction cancels steps that have not
started when cancellation is safe, invalidates unapproved proposals, and
continues from recorded observations. Completed or externally visible effects
remain in the journal with their real reversibility state under
[Rewind](0004.rewind.md).

If the target request is no longer steerable at acceptance, standalone `?`
creates a new request instead. The resulting cell and request identity make
that boundary visible; Genshell never attaches a correction to a completed
request after the fact.

## Queueing with `??`

`??` always creates a new request identity. It never steers, replaces,
coalesces with, or cancels the active request:

```text
$gsh> ? inspect the failing build
...still responding...
$gsh> ?? summarize the latest git diff
queued behind request 41
$gsh> _
```

Queued requests activate in acceptance order when the lane becomes available.
Each queue entry has a request identity, submission identity, queue position,
context generation, cancellation state, deadline policy, and visible cell.

Relevant shell context is identified at acceptance so a delayed request does
not silently become a request about a different directory, command, or
failure. Potentially changing resources are represented by immutable bounded
snapshots or versioned references. Lazy retrieval at activation revalidates
those references and records any detected change instead of silently replacing
the original context.

The AI queue has a fixed capacity. When full, `??` is visibly rejected before
a request identity is committed, or receives an explicit terminal `rejected`
cell if acceptance was already committed. It is never converted to steering,
never overwrites an older entry, and never waits in an unbounded hidden queue.

Cancelling the active request advances the next queued request only after the
active request reaches a terminal cancellation state. Cancelling one queued
request removes only that identity and preserves FIFO order among the others.
Provider failure follows explicit retry or failure policy and cannot cause the
same queued request to execute twice.

## AI lifecycle and identity

An AI request has a stable identity across steering generations:

```text
queued ──> assembling ──> provider-running ──> streaming
  │              │                │                │
  ├──────────────┴────────────────┴───────────────> failed
  ├──────────────────────────────────────────────> cancelled
  └──────────────────────────────────────────────> completed

streaming ── steering ──> next generation ──> streaming
```

Each provider request and event carries:

- stable AI request identity;
- generation number;
- originating submission and cell identity;
- provider attempt identity;
- context generation and provenance references;
- absolute deadline and cancellation state;
- bounded sequence number for ordered streaming events.

The reactor validates all fields before changing a cell. A late chunk from a
cancelled or superseded generation is counted and discarded. It cannot appear
in the revised answer or complete the active request.

AI request identity is distinct from provider conversation, network request,
process, and action identity. Provider retries may change transport identity
without changing the AI request. A steering generation may create a new action
proposal, while executed actions retain their own stable journal identities.

## Latency contract

Managed asynchronous mode adds these PTY-observed metrics:

| Metric | Start | End | Initial target |
| --- | --- | --- | --- |
| Enter-to-next-editor | The PTY harness sends Enter for a complete instruction. | The one-row logical cell is committed, the next base prompt is observable, and the editor accepts a key. | p99 no greater than 5 ms for reactor-owned acceptance and rendering. |
| Output-to-preserved-edit | A job output event becomes readable while text is present in the active editor. | The output is visible in its cell and the exact edit text and cursor are restored. | p99 no greater than 5 ms for a bounded output batch. |
| Steering acceptance | The PTY harness sends Enter for a steering instruction. | The old generation is locally stale, the steering cell exists, and the next editor accepts input. | p99 no greater than 5 ms; provider acknowledgement is excluded. |
| Queue acceptance | The PTY harness sends Enter for `??`. | The distinct queue identity and position are visible and the next editor accepts input. | p99 no greater than 5 ms; provider execution is excluded. |

The deadlines cover only work controlled by the reactor. Process creation,
provider latency, terminal-emulator pixels, filesystem spooling, and external
program execution remain outside the internal deadline, but none may delay the
next editor.

## Resource bounds and overload

Before implementation, each of these receives an explicit fixed or configured
limit and a deterministic full-state policy:

- active and retained cells;
- simultaneously runnable jobs and PTYs;
- queued submissions and AI requests;
- bytes consumed from one job per reactor turn;
- per-cell in-memory output and virtual-terminal state;
- total retained or spooled output;
- render operations and rows per frame;
- pending steering generations and provider events;
- cancellation grace periods and worker restart attempts.

Logical cell growth does not authorize unbounded resident memory. Older output
may be spooled through isolated bounded work, compacted, or replaced by an
explicit truncation marker according to configuration and journal policy. The
reactor never blocks on output persistence. If neither memory nor spool budget
is available, the cell states exactly what was discarded and why.

Under output storms or queue saturation, Genshell prioritizes terminal
ownership, signal and child state, active editing, accepted submissions,
explicit cancellation, then bounded output rendering. It applies backpressure,
fair batching, visible truncation, or rejection according to the affected
resource. It never corrupts the editor to keep up with output.

## Failure and recovery

- A renderer failure restores a documented classic terminal state or exits
  after restoring the original modes; it never leaves hidden input or a lost
  cursor without a diagnostic.
- A PTY failure terminates or detaches only its owning job according to
  explicit policy and leaves other cells editable.
- A job that writes malformed or hostile terminal sequences cannot damage the
  compositor state outside its virtual terminal.
- A provider crash fails or retries only the identified AI generation.
- Steering cancellation cannot terminate an unrelated command or queued AI
  request.
- Terminal resize preserves cells, edit state, focused job state, and PTY
  window sizes under bounded reflow.
- Shell shutdown cancels or hands off every active entity exactly once, writes
  final journal states, restores terminal modes, and leaves no PTY process
  group or provider worker orphaned.

## Compatibility and specification relationships

This specification changes interactive presentation and managed terminal
ownership, not the POSIX shell language. Script input, `-c`, parsing,
expansion, pipelines, redirections, descriptors, and exit statuses remain
governed by [POSIX.1-2024 baseline](0001.principles.md) and the existing
language specifications.

Managed asynchronous mode is a documented Genshell interactive extension.
Classic mode preserves direct foreground-terminal behavior for conformance and
compatibility. The direct handoff rules in
[Real-Time Shell Core](0002.real_time.md) continue to describe classic mode;
the managed-mode ownership and PTY rules in this document take precedence only
while managed asynchronous mode is active.

[LLM Integration](0003.llm.md) continues to govern providers, context,
planning, Unix composition, safety, and privacy. This document adds the
standalone interactive `?` steering rule, the `??` queue rule, and their cell
and generation identities.

[Rewind](0004.rewind.md) records every accepted submission, steering event,
queued request, generated plan, execution, output association, cancellation,
and final state. A superseded AI generation remains auditable and is never
represented as if it had not occurred.

## Implementation groundwork

The current C MVP implements the provider-independent command foundation:
stable bounded cells, one reserved output row, immediate editor activation,
per-job PTYs, up to eight concurrent jobs, a sixteen-cell retained window,
automatic private-input focus, explicit `fg` focus, a global settled-state
indicator, session mode transitions, terminal-sequence containment,
conservative dependency scheduling, and ordered state commits. Classic mode
remains available through configuration, `GSH_REPL=classic`, and `/async`;
non-interactive execution is unchanged. AI request, generation, `?` steering,
and `??` queue state remain future work and are not simulated.

The asynchronous REPL must be built on generic submission and cell concepts,
not on provider-specific placeholders. Before any LLM provider is added, the
runtime architecture reserves representations for:

- submission identity, sequence, kind, lifecycle, and dependencies;
- cell identity, minimum logical rows, output ownership, and final status;
- bounded multi-job registry and per-job output source;
- automatic and explicit editor-versus-job input focus;
- request identity distinct from generation and provider attempt identity;
- steering target, superseded generation, and correction order;
- bounded FIFO AI queue position and terminal state;
- stale-generation rejection at the reactor boundary;
- journal links among submissions, cells, requests, generations, and actions.

Until an AI runtime exists, `?` and `??` need not claim operational support.
The shell must not simulate steering with hidden text replacement or implement
`??` as an unbounded string queue. Parser reservations or disabled diagnostics
may be added only when they preserve ordinary quoted and escaped question-mark
behavior.

The intended implementation order is:

1. generic submission identities, cells, atomic Enter-to-editor rendering, and
   black-box PTY evidence;
2. bounded job PTYs, concurrent output ownership, compositor recovery,
   automatic private-input focus, and explicit fallback focus;
3. dependency-aware scheduling and ordered shell-state commits;
4. provider-independent AI request, generation, steering, and FIFO queue state;
5. deterministic mock-provider verification before any live provider.

Each stage must remain useful and honest without pretending that a later stage
already exists.

## Verification

All normative tests launch the real `gsh` executable through its public PTY or
non-interactive interface. The managed asynchronous suite verifies at least:

- next-editor visibility and accepted keystrokes before a delayed command
  emits output or exits;
- exactly one logical reserved row at the default on a sufficiently large
  terminal, growth on the second output row, and deterministic small-terminal
  behavior;
- preservation of partial edits, cursor state, UTF-8 input, continuation
  prompts, completion state, and cancellation across concurrent output;
- initial `[●]`, `[●]` to `[○]` to `[●]` transitions, and `[○]` while
  any command is stopped or can emit late PTY output;
- muted branch and indicator styling with an explicit reset before `$gsh>`,
  default-color editor and output, and no style leakage across rows;
- atomic ANSI and UTF-8 indicator clipping under narrow viewports and resize;
- attribution of interleaved `stdout`, `stderr`, progress carriage returns,
  colors, control sequences, and reverse-order completions to the correct
  cells;
- late output to cells outside the visible viewport and correct owned
  scrollback redraw;
- hostile terminal sequences that attempt to erase cells, move the editor, or
  forge prompts;
- concurrent independent commands plus queued state-dependent commands;
- immediate independent external dispatch across a long-running compound
  command, plus launch-state mutations that correctly prevent overtaking;
- ordered `cd`, variable, alias, function, option, positional, and `$?`
  semantics under every completion ordering;
- automatic PTY focus for password/private-input cases, default-color editor
  preservation, exact edit restoration, and explicit focus for line-oriented,
  raw-mode, full-screen, stopped, continued, and signal-terminated jobs;
- automatic contained full-screen focus for generic non-canonical PTYs,
  bounded ANSI relay, blocked OSC/DCS/alternate-screen/window controls, resize,
  detach, abnormal-exit restoration, and a compact retained cell record;
- immediate and deferred `/async` transitions, pending cancellation, classic
  background jobs, fresh managed viewports, history retention, configuration
  precedence, and absence of persistent writes from session toggles;
- resize, terminal disconnect, renderer failure, PTY failure, output storms,
  process exhaustion, descriptor exhaustion, queue saturation, and shutdown;
- classic-mode terminal ownership and unchanged non-interactive conformance.

Future deterministic mock-provider tests additionally verify:

- `?` with no active request creates a new stable request;
- `?` during streaming creates a new generation of that request and marks the
  earlier cell superseded;
- a completion-versus-steering race is resolved by reactor acceptance order;
- stale chunks, completion events, plans, and provider errors from superseded
  generations are discarded;
- rapid steering preserves every correction in order while allowing provider
  work to coalesce;
- steering never reverses or duplicates an already executed effect;
- `??` always creates a distinct FIFO request and never steers;
- queued context refers to acceptance-time state and reports revalidation
  changes;
- queue cancellation, full-queue rejection, provider crash, timeout, retry,
  and shutdown preserve identities and execute at most once;
- standalone control syntax cannot be confused with quoted text, escaped text,
  pathname patterns, or the pipeline `?` primitive;
- AI-disabled mode has no provider processes, hidden requests, latency
  dependency, or effect on ordinary command behavior.

The feature is not complete when the prompt merely appears early. Completion
requires proof that the next editor is live, output remains owned, execution
and shell state are deterministic, steering and queueing are unambiguous, and
terminal integrity survives every supported event ordering.
