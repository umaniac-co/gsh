# Rewind

Rewind is Genshell's boot-scoped action journal and local undo system.

> **Reversible when possible, always recorded.**

Rewind does not claim that every side effect can be rolled back. It guarantees that every `gsh` action leaves a structured record and captures enough local state for undo whenever this is technically and materially possible.

> [!note] Algorithm specification deferred
> The implementation algorithms that discover affected resources, capture state, compute diffs, and build the action journal will be specified later. They will necessarily be comprehensive and internally complex, covering concurrency, partial actions, external processes, storage accounting, eviction, failures, crash recovery, and platform differences. This document currently defines Rewind's product semantics and guarantees, not its final diffing and journaling algorithms.

## Action model

An action can originate from a command typed by the user, an AI intent, an AI-generated command sequence, or a native primitive from [OS Automation](0005.os_automation.md). A compound plan is recorded as one action with ordered steps.

For each action, `gsh`:

1. Creates a journal entry before execution.
2. Classifies the expected effects and affected resources.
3. Captures before-state snapshots for supported local mutations when possible.
4. Executes the action.
5. Records the actual effects, result, exit status, and reversibility state.
6. Makes the structured record available to humans and to the LLM as operational context.

A journal entry includes at least:

- action, boot, and session identifiers;
- timestamp, origin, intent, current directory, and displayed commands;
- ordered steps and effect classes;
- affected paths or external resources;
- exit status and result metadata;
- reversibility state and reason;
- snapshot identifier and physical storage used, when available.

The LLM receives the action metadata and reversibility state, not the contents of captured files unless access to those contents is separately required and permitted.

## Reversibility states

- `full`: all recorded effects are covered by an available rollback mechanism.
- `partial`: only some effects can be reversed, typically local file changes within an action that also produced external side effects.
- `none`: no rollback state is available.

The state is explicit in the journal even when no snapshot was created.

Common reason codes include:

- `external_side_effect`
- `snapshot_limit_exceeded`
- `snapshot_evicted`
- `unsupported_resource`
- `unknown_write_set`
- `snapshot_failed`

## Filesystem snapshots

Before a supported local mutation, Rewind captures the file's previous contents and relevant metadata, including permissions, ownership, timestamps, extended attributes, and symlink state where supported.

The snapshot model also records:

- that a newly created path did not previously exist;
- the previous contents and metadata of a deleted path;
- source and destination state for moves and renames;
- directory manifests for structured directory operations.

Snapshots are stored privately on local disk in a boot-scoped runtime area. They survive `gsh` restarts during the same boot and are removed when the computer restarts. If shutdown cleanup cannot run, stale boot data is removed the next time the Genshell runtime starts.

Implementations should prefer copy-on-write clones or reflinks and may use compression and content deduplication. The budget counts physical storage consumed rather than the logical size of referenced files.

## Storage budget

The default snapshot budget is 5 GiB and can be changed in [`~/.gshrc`](0006.gshrc.md):

```text
rewind.max_storage = 5GiB
```

When more room is needed, the oldest snapshots are evicted. Their journal entries remain available, receive `reason: snapshot_evicted`, and are reclassified as `partial` or `none` according to any rollback mechanisms that remain.

If a single action cannot be captured within the configured budget, or snapshot creation is otherwise impossible, the action proceeds without an inline warning. No incomplete snapshot is presented as a complete rollback point. The journal records the action with `reversibility: none` and an explicit reason such as `snapshot_limit_exceeded`.

For mixed actions, supported local effects may still be captured while external effects remain irreversible. Such actions are recorded as `partial`.

## User experience

Rewind is silent during normal execution. Reversibility information is available when requested and is always present in the structured context read by the LLM.

Conceptual commands:

```text
gsh$ actions
gsh$ action show <id>
gsh$ undo
gsh$ undo <id>
gsh$ undo --dry-run <id>
gsh$ redo
```

`undo` restores the latest action with an available snapshot. An explicit action identifier targets an older action and first checks whether later actions depend on the same resources.

Before restoration, `gsh` compares current state with the state recorded after the original action. It never silently overwrites unrelated changes made later by the user or another process. Conflicts are reported and require explicit resolution.

Undo is transactional: either the covered state is restored completely or the previous state is preserved. Undo itself is recorded as an action, allowing redo when its rollback data remains available.

For a `partial` action, only the covered effects are restored and the result states which effects remain irreversible.

## Scope and limitations

Native Genshell primitives and structured AI actions can usually declare their write sets before execution and therefore provide the strongest rollback guarantees.

Arbitrary external programs may modify paths that cannot be predicted in advance. Full support for these commands requires tracked execution through an overlay or another mechanism that observes writes before they reach the underlying filesystem. Until then, actions with an unknown write set are recorded with the appropriate reversibility state rather than being presented as safely undoable.

External effects such as network requests, messages sent to remote services, and changes made in systems outside the local runtime cannot generally be reversed. A semantic adapter may provide a compensating action for some services, but compensation must not be represented as an exact rollback.

## Storage and privacy

- Snapshot storage is private to the user and inaccessible to other local users by default.
- Snapshot data must not be placed in cloud-synchronized directories or included in backups or indexing where the platform allows exclusion.
- Original file permissions and metadata are preserved for restoration.
- Journal metadata may be exposed to the LLM as context; snapshot contents are not exposed automatically.
- Cleanup must be deterministic across normal shutdown, crashes, and the next boot.

## Verification

Black-box tests run the real `gsh` executable and verify:

- creation, modification, deletion, rename, and restoration of files and directories;
- permissions, ownership, timestamps, extended attributes, symlinks, sparse files, and large files;
- atomic multi-file actions and failures during snapshot, execution, and restoration;
- journal recovery after worker or shell crashes;
- storage accounting, eviction, over-budget actions, and boot-scoped cleanup;
- `full`, `partial`, and `none` classification with stable reason codes;
- conflict detection when files change after an action;
- the absence of hidden or partial rollback guarantees;
- consistent action metadata in both human-readable history and LLM context.
