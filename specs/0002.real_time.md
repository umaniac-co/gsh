# Real-Time Shell Core

Genshell applies soft real-time engineering discipline to the interactive behavior it controls while preserving the Unix process, terminal, and job-control model expected from a real shell.

> **Real-time where `gsh` has control. Asynchronous everywhere else.**

The objective is not to make arbitrary external programs complete within a deadline. The objective is to keep the `gsh` core responsive, predictable, and recoverable even when prompts, completions, repositories, plugins, AI providers, or the host system are slow.

## Terminology and boundary

In this specification:

- **POSIX** refers to the portable process, signal, terminal, file-descriptor, clock, and job-control interfaces used by the runtime on macOS and Linux.
- **POSIX shell compatibility** is a separate language-compatibility concern. Using POSIX runtime APIs does not by itself make the `gsh` language conformant with the POSIX `sh` grammar.
- **Soft real-time** means that `gsh` defines latency deadlines, measures deadline misses, bounds work on critical paths, and degrades predictably under load.
- **Hard real-time** means that every deadline is guaranteed by the complete hardware and software stack. `gsh` does not claim hard real-time behavior on general-purpose macOS or Linux systems.
- **Critical path** is work that must complete before the editor can accept or render the next interaction, transfer terminal ownership, or recover the prompt.
- **Optional work** includes prompt enrichment, automatic completion, repository inspection, indexing, telemetry, prefetching, and speculative AI work.

The soft real-time contract covers:

- interactive input and line editing;
- prompt availability and redisplay;
- dispatch performed by the shell itself;
- signal and child-state handling;
- terminal ownership and recovery;
- scheduling, cancellation, and isolation of asynchronous shell work.

It does not cover:

- the execution time of an external program;
- filesystem, network, model-provider, or operating-system latency outside `gsh`;
- terminal-emulator pixel rendering after `gsh` has written output;
- hard deadline guarantees from the kernel scheduler.

## Goals

- Keep typing and line editing responsive while optional work is slow, blocked, or failing.
- Display a usable base prompt without waiting for Git, plugins, version managers, network services, or AI.
- Preserve correct POSIX process groups, signals, pipelines, redirections, and controlling-terminal behavior.
- Use explicit deadlines, bounded queues, cancellation, coalescing, and stale-result rejection.
- Ensure that overload delays or drops optional work instead of blocking the interactive core.
- Keep the correctness-critical shell process single-threaded and make it the sole owner of mutable shell and terminal state.
- Isolate untrusted, extensible, or potentially blocking work in worker processes.
- Provide the same observable contract on macOS and Linux, with platform-specific acceleration hidden behind internal interfaces.
- Make latency and deadline misses observable through local diagnostics and reproducible functional benchmarks.

## Non-goals

- Applying `SCHED_FIFO`, `SCHED_RR`, Mach time-constraint policies, or another elevated scheduler policy to the entire shell.
- Claiming that a program launched by `gsh` is real-time merely because `gsh` launched it.
- Replacing standard terminal and job-control semantics with hidden output proxying.
- Making every subsystem concurrent.
- Optimizing average latency at the cost of worse tail latency, correctness, or recoverability.
- Treating Zsh performance as a correctness oracle or requiring identical internal architecture.

## Latency contract

The initial latency budgets are engineering acceptance targets. They are measured from outside the process through a pseudo-terminal and must be re-baselined on supported operating systems before a stable release.

| Metric | Start | End | Initial target |
| --- | --- | --- | --- |
| Key-to-output, idle | The benchmark writes a key to the PTY master while the editor is idle. | `gsh` writes the corresponding editor update to the PTY. | p99 no greater than 5 ms. |
| Key-to-output, loaded | The benchmark writes a key while the defined stress workload is active. | `gsh` writes the corresponding editor update to the PTY. | p99 no greater than 16 ms. |
| Exit-to-prompt | The benchmark observes that the foreground probe is exiting. | The complete base prompt is observable and the editor accepts input. | p99 no greater than 5 ms. |
| Startup-to-prompt | The benchmark starts a fresh interactive `gsh` process. | The complete base prompt is observable and the editor accepts input. | Recorded and compared with the local Zsh baseline; a fixed target is set after baseline collection. |
| Enter-to-dispatch | The benchmark sends Enter for a known builtin or probe command. | The builtin marker or first probe marker is observable. | Recorded separately for builtins and external processes; external program startup is reported, not attributed entirely to `gsh`. |

Every latency report includes:

- sample count;
- p50, p95, p99, and p99.9 when the sample count supports it;
- maximum observed latency;
- the number and percentage of missed deadlines;
- the operating system, kernel, CPU, power state, terminal size, `TERM`, `gsh` revision, and comparison-shell version;
- whether the run used a fresh process or an already-running interactive session;
- the exact load profile and prompt/completion configuration.

For deadline `D`, the miss rate is:

```text
deadline_miss_rate(D) = samples_above_D / total_samples
```

A lower mean does not compensate for frequent long stalls. Tail latency and missed deadlines are the primary real-time signals.

## Runtime architecture

The correctness-critical `gsh` process is a single-threaded reactor:

```text
terminal input ───────────┐
signal self-pipe ─────────┤
worker result channels ───┼──> reactor ──> editor, shell state, jobs, terminal
child-state changes ──────┤
monotonic timers ─────────┘
```

The reactor is the sole owner of:

- the line editor and render state;
- parser and active command state;
- variables, aliases, functions, current directory, and session environment;
- the job table and process-group relationships;
- prompt generations and completion generations;
- terminal modes and controlling-terminal ownership;
- mutation of user-visible session state.

No worker, provider, plugin, signal handler, or background callback may write directly to the terminal or mutate shell state.

The portable baseline uses:

- `termios` and `isatty()` for interactive terminal handling;
- `poll()` or `pselect()` for readiness and bounded waiting;
- nonblocking `pipe()` or `socketpair()` channels for signals and worker messages;
- `sigaction()` and `sigprocmask()` for signal handling and race prevention;
- `fork()` and `execve()` for the general execution path;
- `posix_spawn()` only as a verified fast path with equivalent semantics;
- `pipe()`, `dup2()`, `close()`, and close-on-exec descriptors for pipelines and redirections;
- `setpgid()` and `tcsetpgrp()` for job control;
- `waitpid()` with `WNOHANG`, `WUNTRACED`, and `WCONTINUED` for child-state collection;
- `clock_gettime(CLOCK_MONOTONIC, ...)` for deadlines and durations.

The reactor must not depend on `kqueue`, `epoll`, `signalfd`, `timerfd`, Mach scheduling policy, or Linux real-time scheduling for correctness. Optional `kqueue` and `epoll` backends may be added behind the same internal event interface after the portable implementation is measured. Backend selection must not change user-visible semantics.

## Reactor rules

Each reactor iteration must:

1. calculate the nearest monotonic deadline;
2. build or update the readiness set;
3. wait no longer than the nearest deadline;
4. process a bounded batch of ready critical events;
5. process a bounded batch of non-critical results;
6. perform pending render work once;
7. return to readiness polling before one source can starve the others.

While it is servicing interactive or job-control events, the reactor must not perform:

- filesystem traversal;
- repository inspection;
- network access;
- model invocation;
- plugin-defined blocking work;
- unbounded parsing, formatting, logging, or output capture;
- a blocking wait for a child or worker;
- a blocking mutex acquisition;
- an unbounded drain of one event source while terminal input or child state remains pending.

Buffers, event arrays, queues, messages, captured output, and diagnostic records have explicit limits. If a limit is reached, `gsh` applies the documented overload policy instead of growing without bound.

## Event priority and overload

Event classes are ordered by the state they protect, not merely by arrival time:

1. terminal ownership, child-state changes, and required signal handling;
2. editor input, cancellation, and rendering while the editor owns the terminal;
3. accepted commands and explicit user-requested completion;
4. prompt enrichment and automatic completion;
5. indexing, prefetching, diagnostics, and speculative AI work.

Under pressure, `gsh` must:

- preserve terminal and job-control correctness;
- preserve already-accepted user commands exactly once;
- coalesce repeated resize, redisplay, prompt, and automatic-completion requests;
- cancel or discard work whose generation is stale;
- reject new optional work when its queue is full;
- expose overload and deadline misses through diagnostics;
- keep accepting interactive input whenever the shell owns the terminal.

Optional work must never displace accepted commands or correctness-critical events. Overload behavior must be deterministic for the same observable state and configuration.

## Signals and child state

Signal handlers perform only async-signal-safe notification. They may set a `volatile sig_atomic_t` flag and write a byte to a nonblocking self-pipe. They must not allocate memory, format output, update the job table, invoke providers, or redraw the terminal.

When the self-pipe becomes readable, the reactor:

1. drains the notification bytes without blocking;
2. snapshots and clears pending signal flags safely;
3. calls `waitpid(-1, ..., WNOHANG | WUNTRACED | WCONTINUED)` until no more child transitions are available;
4. updates jobs and pipelines in the main process;
5. schedules at most one necessary notification or redisplay.

`SIGCHLD` is blocked around process creation and job-table insertion so a short-lived child cannot terminate before it is tracked. Process-group setup is performed in both the parent and child where required to close POSIX job-control races. Expected race errors such as a child that has already executed or exited are classified explicitly rather than treated as generic failure.

Every accepted command is assigned one stable execution identity. Retries after `EINTR`, `EAGAIN`, partial writes, or process-creation pressure must never cause the command to be recorded or executed twice.

## Terminal and job control

At interactive startup, `gsh` establishes or validates its process group, obtains control of the terminal, records the original terminal modes, and enters editor mode only while its process group owns the terminal.

The direct handoff rules below govern classic mode. In the default managed
asynchronous REPL, the shell retains the physical terminal and applies the
per-job PTY, cell, focus, and scheduling rules in
[Asynchronous REPL](0008.async_repl.md). Script and `-c` execution are
unchanged.

For a foreground job, `gsh`:

1. completes pipes and redirections;
2. creates the job process group;
3. restores the terminal mode expected by child programs;
4. transfers the controlling terminal with `tcsetpgrp()`;
5. stops reading editor input while the foreground job owns the terminal;
6. continues processing child-state and internal non-terminal events without blocking in `waitpid()`;
7. reclaims the terminal when the job exits or stops;
8. restores the editor terminal mode;
9. publishes job status and displays a usable prompt.

Failures, signals, stopped jobs, worker crashes, parse errors, end-of-file, and normal exit must all restore the terminal to a documented valid state. A worker can never own the controlling terminal.

Foreground jobs inherit the terminal directly unless the user requests a redirection or a feature explicitly requires a PTY. `gsh` must not silently proxy ordinary foreground output through pipes merely to improve rendering or benchmarks, because doing so changes `isatty()`, buffering, colors, signals, and job-control behavior.

Background-job output follows normal file-descriptor and terminal semantics. `gsh` may redraw its own editor after output it can observe, but it must not claim that arbitrary direct terminal writes from another process can always be intercepted or ordered.

## Command execution

State-changing builtins such as `cd`, environment mutation, job-control commands, and configuration changes execute in the main shell process because their effects belong to the active session. Time spent performing explicitly requested builtin or shell-language work is command execution, not an interactive-editor deadline while the editor is inactive. This semantic requirement must not be bypassed by silently moving stateful execution to a worker. Cancellable waits and explicit resource limits still apply where the command's semantics permit them.

The general external-command path uses `fork()` followed by a minimal child setup and `execve()`. Before `execve()`, the child performs only operations safe for the post-fork context: process-group setup, signal disposition, descriptor duplication and closure, and execution. Failure is reported through a dedicated close-on-exec channel and terminates with `_exit()`.

`posix_spawn()` may be used for a command only when its file actions, process group, signal state, redirections, and error reporting are observably equivalent to the general path on both supported operating systems. It is an optimization, not a separate semantic path.

Pipelines are created as one job with one process group. The shell closes unused pipe ends deterministically in both parent and children. A pipeline is not complete until all state required by the shell's selected pipeline semantics has been collected.

Parsing, expansion, globbing, and command dispatch are measured independently from external execution. Potentially large expansion is command work, not editor work, but it remains bounded by configured resource limits and must remain cancellable where semantics permit.

## Asynchronous worker model

Potentially blocking or extensible work runs in persistent worker processes rather than threads inside the correctness-critical shell process. This keeps the main process single-threaded and avoids unsafe interactions between a multithreaded allocator or plugin and the `fork()` execution path.

Worker communication uses framed messages over nonblocking pipes or `socketpair()` channels. Every request includes:

- a stable request type and protocol version;
- a request identifier;
- a context generation;
- an absolute monotonic deadline when applicable;
- an immutable, bounded snapshot of the required context;
- cancellation and maximum-result-size policy.

Workers receive only the context required for the request. They do not receive pointers into shell state and do not share mutable shell memory. Results return through the reactor and are validated before use.

If a worker stalls, exceeds its deadline, returns malformed data, closes its channel, or crashes, the reactor marks the request failed, preserves the interactive core, and restarts or disables the worker according to bounded policy. Restart attempts are rate-limited and cannot create an unbounded process loop.

AI-provider behavior follows the same isolation and deadline rules and the additional contract in [LLM Integration](0003.llm.md).

## Prompt behavior

The prompt is split into:

- a synchronous base containing only bounded local state already owned by the shell;
- asynchronous segments for repository state, external tools, plugins, network data, or other potentially slow sources.

The base prompt appears without waiting for asynchronous segments. Each prompt request carries a generation tied to the relevant directory, environment, previous status, and prompt configuration. A result is applied only if its generation is still current and the editor is active.

Applying an asynchronous prompt result is a main-reactor operation. It performs one coherent redisplay and must preserve the current edit buffer, cursor, selection, undo state, and terminal dimensions. A stale result is discarded without visible effect.

## Completion behavior

Explicit completion and automatic suggestions are separate priority classes. Both operate on an immutable snapshot containing the buffer, cursor, directory, relevant environment, and completion generation.

Editing the line increments its generation. A completion result is eligible only when it still matches the active generation and context. Old results are discarded; they may populate a bounded cache only when their cache key remains valid.

Directory scanning, PATH search, repository inspection, external completion programs, and AI completion never execute in the reactor. Explicit completion may display a bounded pending state, but automatic completion must never block typing.

Cancellation is cooperative first and enforced by worker termination only after a bounded grace period. Repeated keystrokes coalesce automatic requests instead of creating an unbounded queue.

## Timing and diagnostics

All internal durations and deadlines use a monotonic clock. Wall-clock changes must not extend, shorten, or reorder a deadline.

The reactor records bounded local diagnostic events for:

- key received and editor output committed;
- line accepted and dispatch started;
- process creation requested and completed;
- child transition observed and processed;
- terminal reclaimed and base prompt committed;
- worker request, cancellation, deadline, completion, and stale-result discard;
- reactor iteration duration, queue depth, and overload action;
- missed internal and user-visible deadlines.

Diagnostics use a bounded ring buffer and must not perform blocking I/O on the critical path. Persistent logs, if enabled through [`~/.gshrc`](0006.gshrc.md), are written asynchronously and obey redaction and size limits. Product telemetry remains opt-in and is not required for local performance analysis.

## Functional verification

All normative verification exercises the real `gsh` executable through public interfaces. The test suite does not rely on internal unit tests as evidence for this contract.

### PTY harness

The benchmark and functional harness:

1. creates an isolated pseudo-terminal;
2. starts the real shell as an interactive session leader with a controlling terminal;
3. configures a plain unique prompt marker and deterministic environment;
4. sends actual bytes, commands, control characters, resize events, and signals;
5. observes raw terminal output, process state, filesystem effects, and exit status;
6. uses monotonic timestamps at the PTY boundary;
7. waits for semantic markers and process events rather than arbitrary sleeps;
8. records every raw sample in a machine-readable result before aggregation.

The harness uses a minimal compiled probe for external-process measurements. The probe emits stable lifecycle markers without shell-script startup noise. Builtin and external dispatch are reported separately.

Key-to-output measures bytes produced by `gsh`, not terminal-emulator pixel presentation. Any end-to-end visual benchmark is a separate test and identifies the terminal emulator explicitly.

### Zsh comparison

Every supported operating system compares `gsh` with the Zsh installed on the same machine. Runs alternate or randomize shell order to reduce thermal, scheduler, and cache bias.

Results are reported in three profiles:

- **Zsh clean:** startup files and third-party plugins disabled;
- **Zsh feature parity:** prompt and completion functionality matched as closely as possible to the tested `gsh` configuration;
- **gsh:** the corresponding `gsh` configuration.

Absolute macOS and Linux timings are not compared as if they came from the same environment. Each platform reports absolute values and its local `gsh`-to-Zsh ratio. Zsh is a performance baseline; it is not an oracle for intentional `gsh` language differences.

### Load profiles

The suite measures at least:

- idle interactive editing;
- CPU saturation by controlled helper processes;
- filesystem activity in isolated temporary directories;
- large directories and large PATH values;
- large repositories and intentionally slow repository providers;
- large histories and completion candidate sets;
- concurrent prompt and completion requests;
- queue saturation and repeated stale generations;
- many short-lived foreground and background jobs;
- `SIGCHLD` and `SIGWINCH` bursts;
- stalled, malformed, terminated, and repeatedly crashing workers;
- external commands that exit immediately, stop, continue, ignore signals, or close descriptors unexpectedly.

### Reliability guardrails

Performance results are invalid unless the same run verifies:

- no accepted command is lost or executed more than once;
- no stale asynchronous result reaches the active prompt or editor state;
- process groups and controlling-terminal ownership are correct;
- `Ctrl-C`, `Ctrl-Z`, `fg`, `bg`, pipelines, and redirections retain their specified behavior;
- the terminal is recovered after success, error, cancellation, signal, worker failure, and shell shutdown;
- no zombie process remains after the shell has observed its child transition;
- no file descriptor or worker process grows without its configured bound;
- no deadlock, livelock, crash, memory-safety violation, or unbounded restart loop occurs;
- the shell remains usable when every optional worker is unavailable.

Functional property-based tests generate command lines, quoting, expansions, redirections, pipeline shapes, signals, and event orderings and run them through the executable. Black-box fuzzing targets interactive and non-interactive entry points. Sanitizer builds run the same functional scenarios on macOS and Linux.

Fault-injection builds exercise `EINTR`, `EAGAIN`, `EMFILE`, `ENOMEM`, partial I/O, closed channels, process-creation failure, and worker termination through the real executable. Fault injection must not bypass the public shell lifecycle being asserted.

## Release acceptance

A release satisfies this specification only when:

- the functional PTY suite passes on supported macOS and Linux versions;
- all reliability guardrails pass under the defined stress profiles;
- latency reports contain raw samples and the required environment metadata;
- the initial p99 deadlines pass or an explicit, reviewed exception documents the regression and its cause;
- no new critical-path operation lacks a bound, deadline, cancellation rule, or overload behavior;
- the clean and feature-parity Zsh comparisons are both published for the release benchmark environment;
- failures remain explicit and never become silent command loss, duplication, terminal corruption, or stale-state application.

Real-time performance is therefore treated as a continuously verified behavioral contract, not as a claim derived from implementation language, scheduler priority, or average benchmark speed.
