# OS Automation

Genshell OS Automation is the structured runtime through which humans and agents operate the local computer. “Computer use” is its interactive edge, not the whole feature: UI automation sits beside native control of files, processes, services, applications, windows, displays, clipboard, networking, devices, and system events.

> **OS primitives before UI imitation.** Use the strongest semantic interface available. Accessibility automation is a fallback; visual coordinate control is the last resort.

## Goals

- Expose the computer as typed resources, operations, observations, and events rather than as a collection of shell commands or screenshots.
- Give humans, `gsh`, Codex, and other agents the same versioned runtime contract.
- Preserve one mental model across macOS, Linux, and Windows while allowing different native implementations.
- Combine filesystem, process, application, window, UI, and other OS operations in one observable plan.
- Return structured results while retaining a readable shell representation and traditional exit semantics.
- Observe the state after every operation, verify postconditions, and adapt without relying on arbitrary sleeps.
- Keep normal shell behavior independent from the AI provider and from the availability of desktop automation.

## Non-goals

- Building a remote desktop product.
- Treating screenshots, mouse coordinates, or generated Bash as the primary API of the computer.
- Pretending that every capability is available on every desktop environment.
- Giving Genshell more authority than the current user or bypassing platform permission systems.
- Recreating POSIX on Windows or building “Cygwin 2”.

## Architecture

```text
human or agent intent
        ↓
typed plan and resource references
        ↓
capability, permission, and effect policy
        ↓
Genshell OS Runtime
        ↓
platform adapter: macOS / Linux / Windows host
        ↓
execute → observe → verify → adapt
        ↓
structured result + Rewind action journal
```

The runtime is independent from the model. `gsh`, Codex, local models, and future agents are clients; they do not own the interface to the computer.

Adapter selection, fallbacks, observation, and effect policy are configured through [`~/.gshrc`](0006.gshrc.md). Configuration can restrict runtime authority but cannot bypass native platform permissions.

Every operation has:

- a stable operation name and version;
- typed arguments and resource references;
- declared capabilities and effect classes;
- preconditions and postconditions;
- a deadline, cancellation behavior, and retry policy;
- a structured result and stable error code;
- a human-readable representation;
- an action-journal entry with reversibility metadata.

Compound requests are represented as dependency-aware plans. Independent read operations may run concurrently, while UI operations that share focus or input state are serialized.

## Semantic hierarchy

For every task, the planner selects the highest available level:

1. Application or domain API.
2. Native OS primitive.
3. Accessibility tree and semantic UI action.
4. Keyboard shortcut or synthesized input.
5. Screenshot, vision, and screen coordinates.

The selected level is recorded for each step. Falling back never changes an operation from “unsupported” to “successful” without exposing the weaker mechanism and its limitations.

Direct invocation is preferred over manipulating global focus. Event subscriptions and semantic postconditions are preferred over polling; bounded polling is preferred over fixed sleeps.

## Resource model

Resources are represented by typed descriptors rather than raw pointers, transient accessibility objects, window handles, or unqualified paths. Descriptors identify their platform realm and carry only the metadata required by the client.

Examples include:

- files and directories;
- processes, jobs, and services;
- applications and documents;
- windows, displays, workspaces, and desktop sessions;
- accessibility elements;
- clipboard items and notifications;
- network interfaces, listeners, and connections;
- mounted volumes and selected devices.

Handles are stable only for their declared lifetime. When a window, process, or UI element disappears, the runtime returns a stale-resource error and may re-resolve the original semantic selector when safe.

## Primitive namespaces

The initial semantic surface should include operations such as:

```text
system.info()

service.list()

app.list()

app.quit(app)

window.list()

ui.snapshot(scope)

```

Platform-specific extensions may exist, but the portable subset has normative semantics and a shared conformance suite.

## Capabilities and effects

`system.capabilities()` reports each operation as `available`, `permission_required`, `degraded`, `unavailable`, or `unsupported`, together with the active adapter and any relevant limitation.

Operations declare one or more effect classes:

- `read_only`
- `local_write`
- `process_control`
- `network`
- `destructive`
- `privileged`
- `gui_side_effect`

Clients receive only the capabilities granted to them. Native permission dialogs, sandbox boundaries, Accessibility consent, screen-capture consent, portals, and UAC remain authoritative. Genshell never silently elevates privileges or converts a denied capability into simulated input.

All native operations have a readable representation, for example:

```text
window.move(app: "Visual Studio Code", display: 1, frame: "left-half")
```

This representation appears in the action journal even when no shell command was generated.

## Observation and context

The runtime maintains structured operational context for the current desktop session, including applications, processes, windows, displays, focus, active workspaces, recent events, and the results of previous actions.

Observation uses semantic state first. Screenshots are captured only when visual information is necessary or no structured interface exists. Sensitive element values and secure text fields are redacted from observations and logs by default.

Operations return both their result and the observations used to verify it. A successful transport call is not a successful operation unless the requested postcondition is satisfied.

The event stream supports process lifecycle, filesystem changes, service state, application launch and termination, window changes, accessibility notifications, display changes, and adapter availability. Events are bounded, cancellable, and tagged with their source and confidence.

## UI automation

UI elements are addressed through semantic selectors based on attributes such as application, role, name, label, value, state, and ancestry. Selectors must not depend on localized display text when a stable identifier or role is available.

The runtime can:

- inspect the accessible tree;
- find one or more matching elements;
- invoke supported actions directly;
- read and set supported values;
- subscribe to accessibility events;
- recover from stale elements by re-running a selector;
- use synthesized input when direct invocation is unavailable;
- use screenshots and vision only as an explicitly degraded fallback.

Coordinate actions include the target display, scale, coordinate space, and visual evidence used to choose the point. They expire when the relevant window layout changes.

Only one automation action owns global focus and synthesized input at a time. Other agents may continue using non-UI primitives concurrently.

## Automation plans

A plan is an ordered or dependency-based set of typed operations. Each step declares its effects, timeout, required capabilities, postcondition, and safe retry behavior.

For example:

```text
gsh$ ? take the PDF I just downloaded, move it into the project,
       open it, and place the editor on the left and the PDF on the right
```

The runtime can resolve this into filesystem discovery and move operations, application launch, window discovery, display layout, and two window placement operations. Each step is individually observed and recorded, while the complete sequence remains one action.

Retries are allowed only when an operation is idempotent or the runtime can prove that the requested postcondition has not already been reached. Cancellation propagates to unfinished dependent steps and to owned process groups.

## Rewind integration

Every automation plan and primitive is written to the [Rewind](0004.rewind.md) action journal.

- Local mutations receive before-state snapshots when supported and within budget.
- Reversible UI or window operations may store a semantic compensating state.
- Network and other external effects are normally recorded as non-reversible.
- Mixed actions are marked `partial` when only some effects can be restored.
- The journal records the adapter, semantic level, capabilities, observations, result, and reason when reversal is unavailable.

The LLM receives this metadata as context but does not automatically receive snapshot contents or sensitive UI values.

## macOS adapter

The macOS adapter combines Unix and Darwin primitives with:

- Accessibility and `AXUIElement` for semantic UI discovery, actions, values, and notifications;
- Quartz Window Services and CoreGraphics for window enumeration, geometry, displays, and visual capture where permitted;
- `NSWorkspace` and current Launch Services APIs for launching applications, opening files and URLs, and observing application lifecycle;
- Apple Events for applications that expose a semantic automation interface;
- native process, filesystem, networking, notification, and service facilities, including `launchd` where appropriate.

The capability report distinguishes Accessibility, Automation, Screen Recording, protected-file access, and other permissions. Missing consent produces a stable permission error and never triggers an undisclosed visual fallback.

## Linux adapter

The Linux adapter combines POSIX facilities with desktop-session services:

- AT-SPI for semantic accessibility trees, actions, values, and events;
- D-Bus for application, desktop, notification, and service integration;
- XDG Desktop Portal for mediated file access, opening resources, screen capture, clipboard, and Remote Desktop sessions;
- Wayland protocols and desktop-specific adapters only when exposed by the compositor;
- X11 automation as a fallback when an X11 session is active;
- `systemd` user and system services when available, with portable service semantics above the adapter.

Wayland intentionally restricts global inspection and input injection. Genshell uses portals and user consent rather than assuming X11-style authority. Unsupported compositor capabilities remain explicit.

## Windows through WSL

The first Windows implementation uses a split architecture:

```text
gsh and POSIX runtime inside WSL
            ↕ versioned authenticated IPC
signed per-user genshell-host.exe on Windows
            ↓
Win32, UI Automation, Windows applications and desktop
```

Inside WSL, `gsh` controls Linux resources through the Linux adapter. Windows resources are handled by `genshell-host.exe`, which exposes the same semantic runtime contract through:

- Microsoft UI Automation for accessible UI trees, properties, control patterns, actions, and events;
- Win32 APIs for windows, application activation, process lifecycle, clipboard, displays, input, and services;
- `CreateProcess`, ConPTY, and Job Objects where Windows process and terminal semantics are required;
- Windows Graphics Capture for window or display observation when permission and session state allow it.

WSL can launch Windows `.exe` programs directly, but persistent automation should use the structured host connection instead of repeatedly generating PowerShell or command-line glue.

The bridge:

- is scoped to the current Windows user and interactive desktop session;
- authenticates each WSL runtime with a short-lived session secret;
- does not expose a remotely reachable control port;
- negotiates protocol and capability versions;
- isolates host crashes from the shell core;
- distinguishes Windows paths and WSL distribution paths in typed resource descriptors;
- normalizes results without hiding differences in process, path, permission, or window semantics.

UAC and higher-integrity windows remain protected by Windows. The host reports permission and integrity boundaries rather than attempting to bypass them.

## Native Windows

A later native Windows shell backend can implement the same runtime contract directly with Win32, ConPTY, Job Objects, UI Automation, and other native APIs. It keeps the Genshell syntax and mental model without attempting to emulate a complete POSIX kernel.

The WSL bridge and native backend must pass the same portable conformance suite. Platform-specific extensions remain namespaced and capability-discovered.

## Reliability and concurrency

- All operations have explicit deadlines and cancellation.
- UI waits are driven by accessibility, window, or application events whenever possible.
- Optional or stale observations are discarded instead of blocking the interactive shell.
- Adapter crashes cannot corrupt the shell core or terminal state.
- Resource handles are invalidated deterministically when their underlying object disappears.
- Global focus and input are serialized; independent read-only OS operations may run concurrently.
- An operation is complete only after its postcondition is observed or a precise failure is returned.

## Privacy and security

- The runtime applies least-privilege capabilities per client and per action.
- Sensitive clipboard data, secure fields, credentials, and protected content are not included in model context by default.
- Screen capture and UI inspection are limited to the granted desktop session and platform permission boundary.
- Privileged, destructive, network, and GUI effects remain explicitly classified in the plan and journal.
- OS permission prompts and user-consent surfaces are never bypassed.
- IPC between WSL and the Windows host is authenticated, local, versioned, and auditable.

## Verification

The conformance suite runs the real runtime and platform adapters against controlled desktop applications and OS fixtures. It verifies:

- capability discovery and permission-denied behavior;
- files, processes, services, applications, windows, displays, clipboard, network observation, and UI primitives;
- semantic selector stability across changing layouts and localized interfaces;
- multi-display geometry, scale factors, virtual desktops, minimized and occluded windows;
- event-driven waits, stale resources, timeouts, cancellation, retry safety, and adapter crashes;
- focus ownership and concurrent clients;
- Wayland portal sessions and explicit compositor limitations;
- WSL path realms, protocol versioning, host restart, Windows session changes, and integrity boundaries;
- fallback ordering from native semantics to accessibility and finally vision;
- action-journal visibility, effect classification, and [Rewind](0004.rewind.md) metadata;
- equivalent end-to-end workflows across supported platforms.
